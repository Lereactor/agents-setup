# Дизайн: агент-продукты (ВкусВилл, через официальный MCP)

Дата: 2026-09-17 (спроектирован и доведён до рабочего состояния в тот же день)
Статус: **работает** — проверено вживую в группе «Lev's assistants»
(запросы «найди овсянку», «собери продукты на борщ» дали корректный
результат со ссылкой на корзину).

## Контекст

Четвёртый агент в системе (после `news-digest`, `watchdog`, `shopping`).
ВкусВилл выложил официальный MCP-сервер (`https://mcp.vkusvill.ru/mcp`) —
структурированные инструменты поиска товаров, деталей, штрихкодов, аналогов,
скидок, рецептов, магазинов и создания ссылки на корзину. В отличие от
`shopping` (Ozon/Я.Маркет — только веб-поиск по чужим страницам, без API),
здесь есть честные структурированные данные от первого лица — не нужно
разруливать «сколько на самом деле стоит товар у разных продавцов» (см.
Инцидент 7 в `2026-08-20-shopping-agent-design.md`).

Решение: **отдельный Routine** `grocery`, не расширение `shopping` — разная
предметная область (один конкретный магазин, свой источник данных), отдельный
триггер, но **общий Cloudflare Worker**-слушатель с `shopping` — не стоит
заново отлаживать self-trigger loop, дедуп по `update_id`, `waitUntil`, режим
секретаря и т.п., это уже решено один раз в `shopping-listener-worker.js`.

## Триггер

Корни (регистронезависимо, substring): `вкусвилл`, `продукт` (покрывает
«продукты», «продукт», «продуктов» и т.п.).

**Приоритет в слушателе:** сначала проверяются корни `grocery`
(`вкусвилл`/`продукт`), и только если ни один не совпал — корни `shopping`
(`куп`/`заказ`/`найд`/`buy`/`order`/`find`). Это гарантирует, что «купи
продукты» или «вкусвилл, купи молоко» уходит **только** в `grocery`, а не в
оба агента разом.

Формат payload идентичен `shopping`: `{chat_id, message_id,
business_connection_id, text, photo_file_id}` — фото с подписью и реплай
текстом на фото поддерживаются так же (уже реализовано в `extractCandidate`,
переиспользуется без изменений).

## Архитектура

Тот же двухзвенный паттерн, что у `shopping`:

**Звено 1 — общий слушатель** (`scripts/shopping-listener-worker.js`,
переименован по сути в мульти-агентный, файл не переименовывается, чтобы не
трогать уже настроенный Telegram-вебхук). Добавлена функция маршрутизации:
проверяет grocery-корни первыми, затем shopping-корни, и дёргает
соответствующий `fire`-эндпоинт. Два независимых набора секретов:
`ROUTINE_TRIGGER_URL` / `ROUTINE_TRIGGER_TOKEN` (уже существуют, для
`shopping`) и новые `ROUTINE_TRIGGER_URL_GROCERY` /
`ROUTINE_TRIGGER_TOKEN_GROCERY` (для `grocery`).

**Звено 2 — Routine `grocery`.** Триггер — API (`fire`), как у `shopping`.
Вместо веб-поиска использует MCP-сервер ВкусВилла, подключённый через
`.mcp.json` в корне репозитория (см. ниже) + домен `mcp.vkusvill.ru` в
Allowed domains настроек Routine (без этого Routine физически не достучится
до сервера — сеть в облачном окружении Routine по умолчанию ограничена).

## `.mcp.json`

```json
{
  "mcpServers": {
    "vkusvill": { "type": "http", "url": "https://mcp.vkusvill.ru/mcp" }
  }
}
```

Аутентификация не заявлена сервисом публично — не проверено вживую до
первого реального вызова. Если понадобится API-ключ — добавить блок
`"headers": {"Authorization": "Bearer ${VKUSVILL_TOKEN}"}` и переменную
окружения `VKUSVILL_TOKEN` в Routine.

## Инструменты ВкусВилл MCP (по документации сервера)

- `vkusvill_products_search` — поиск по тексту, сортировка (популярность/
  рейтинг/цена), пагинация по 10
- `vkusvill_product_details` — состав, КБЖУ, фото, рейтинг, цена по id
- `vkusvill_product_barcode` — по штрихкоду
- `vkusvill_product_analogs` — аналоги по id товара
- `vkusvill_products_discount` — товары со скидкой
- `vkusvill_cart_link_create` — ссылка на корзину, до 20 товаров
- `vkusvill_recipes` — рецепты с ингредиентами
- `vkusvill_shops` — магазины (адрес, часы, особенности)

Заказа/оплаты через MCP нет — агент доводит дело до ссылки на корзину,
оплату и подтверждение пользователь делает сам в приложении ВкусВилл.

## Промпт Routine `grocery` (черновик, вставляется в UI Routines)

```
Ты — агент-покупки продуктов ВкусВилл. Тебя вызывают через API-триггер
каждый раз, когда в Telegram кто-то упомянул ВкусВилл или продукты.

КРИТИЧЕСКИ ВАЖНО: у тебя НЕТ памяти о предыдущих вызовах в этой сессии.
Каждый вызов обрабатывай так, будто это единственное и первое сообщение.
Даже если в истории сессии есть более ранние сообщения с похожим JSON —
ПОЛНОСТЬЮ ИГНОРИРУЙ их. Работай ИСКЛЮЧИТЕЛЬНО с JSON из самого последнего
(самого нижнего) сообщения сессии.

Каждый вызов добавляет отдельную реплику с JSON-строкой вида:

{"chat_id": ..., "message_id": ..., "business_connection_id": "" или "...",
 "text": "...", "photo_file_id": "" или "..."}

1. Прочитай text целиком и реши: это реальная просьба найти/купить
   конкретный продукт (в т.ч. рецепт/скидки/магазин), или слово попало
   случайно (обсуждение не по теме, слишком расплывчато). Если не похоже
   на реальный запрос — сразу переходи к шагу 7 со status=skipped, в
   Telegram НИЧЕГО не пиши.

   Если это реальный запрос — выдели явные ограничения: бюджет, бренд,
   объём/вес, диетические ограничения (без глютена, без сахара и т.п.),
   количество. Не придумывай то, чего нет в тексте.

2. Если photo_file_id не пусто:
   - вызови getFile через Bot API, получи file_path
   - скачай файл по https://api.telegram.org/file/bot${TELEGRAM_BOT_TOKEN}/{file_path}
   - опиши товар (категория, бренд/модель если видно, отличительные детали)
   - это описание + текст из поля text вместе формируют поисковый запрос

3. Вызови vkusvill_products_search с этим запросом (сортировка по
   рейтингу/популярности, если пользователь явно не просил иное). Если
   пользователь явно спросил про скидки — дополнительно/вместо
   vkusvill_products_discount. Если явно попросил рецепт — vkusvill_recipes.
   Если спросил про магазин/часы работы — vkusvill_shops (только по
   явному запросу, не добавлять по умолчанию в обычный ответ про товар).

4. Отфильтруй результаты по ограничениям из шага 1 (бюджет, бренд, объём,
   диетические ограничения). Если у кандидатов разный вес/объём — приведи
   цену к единой единице (₽/кг, ₽/л) для честного сравнения. Если нужно
   уточнить состав/КБЖУ (пользователь спросил про это, или для проверки
   диетического ограничения) — vkusvill_product_details по кандидату. Если
   у лучшего кандидата нет в наличии — попробуй vkusvill_product_analogs.

   Если после фильтра ничего не осталось — не расширяй критерии молча:
   покажи это как есть и отметь в шаге 6.

5. Выбери топ-2-3 варианта, балансируя цену/рейтинг/наличие — то же правило
   tie-break, что у агента shopping: при сопоставимом рейтинге (разница
   ≤0.2) и одинаковом наличии рекомендуй более дешёвый; отход от самого
   дешёвого — только с явным числовым обоснованием (рейтинг/отзывы/
   наличие). В отличие от Ozon/Я.Маркет здесь один авторитетный источник
   цены на товар — не нужно сверять несколько результатов поиска между
   собой, данные MCP считаются достоверными.

6. Вызови vkusvill_cart_link_create с выбранными товарами (до 20) — если
   шаг 3-5 действительно про покупку (не про рецепт/магазин без товара).

   Отправь ответ в Telegram Bot API sendMessage, ОБЯЗАТЕЛЬНО с
   reply_to_message_id=message_id, chat_id=chat_id (оба из ПОСЛЕДНЕГО
   JSON), и business_connection_id из того же JSON, если оно не пусто.

   🛒 {что искали} — {явные ограничения, если были}

   1. {название} — {цена} ₽ ({₽/кг или ₽/л, если сравнивали разные объёмы}),
      ★{рейтинг} ({N} отзывов, если есть){, нет в наличии — если так}
      {1 фраза почему подходит}

   2. ...

   🔗 Корзина: {ссылка из vkusvill_cart_link_create}

   💡 {краткая рекомендация: что бы взял сам агент и почему}

   (если ограничение было, но под него ничего не подошло:)
   ⚠️ В рамках {бюджета/бренда/etc} ничего не нашлось — ближайшее показано
   выше вместо строгого совпадения.

   Если MCP-вызов не удался или поиск пуст — короткое сообщение об этом
   (НЕ молчание) — молчание допустимо только при status=skipped на шаге 1.

7. Залогируй запуск на Sheets-вебхук (как остальные агенты):

   curl -s -L -X POST "${SHEETS_LOG_URL}" \
     -d "token=${SHEETS_LOG_TOKEN}" \
     -d "agent=grocery" \
     -d "status=success|skipped|error" \
     -d "timestamp=$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

Environment variables Routine: `TELEGRAM_BOT_TOKEN`, `SHEETS_LOG_URL`,
`SHEETS_LOG_TOKEN` — те же три, что у `shopping` (можно скопировать из его
Edit environment).

## Ошибки и логирование

Как у `shopping`: тишина только при `status=skipped` (не похоже на реальный
запрос); любая другая неудача (MCP недоступен, пустой поиск) — короткое
сообщение в Telegram, не молчание. Лог — тот же Sheets-вебхук, `agent=grocery`,
подхватывается существующим мониторингом `watchdog` без изменений (событийные
агенты уже учтены его правилом «вспышка >10 запусков/час»).

## Открытые вопросы / риски

- Триггер-корень `продукт` шире, чем `вкусвилл» — как и в `shopping`,
  расплывчатость гасится LLM-решением на шаге 1 (skip при неуверенности), а
  не сужением корня; если после недели эксплуатации будет много ложных
  срабатываний — сузить корень или требовать оба слова вместе.
- Аутентификация MCP не понадобилась — `.mcp.json` без `headers` работает.

## Инциденты и фиксы (хронология отладки 2026-09-17)

### 1. Локальные коммиты не были запушены на GitHub

Первый реальный тест дал тишину в Telegram. Причина: Routine клонирует
репозиторий **с GitHub**, а `.mcp.json` (и всё остальное для этого агента)
существовал только в локальных коммитах — `git push` забыт. Агент не нашёл
ни одного `vkusvill_*` инструмента (`ListConnectors` вернул `[]`), сам
корректно определил это как сбой и отправил в Telegram предупреждение
вместо молчания — сработало как задумано, просто причина была в
инфраструктуре, а не в промпте. **Урок**: после любого коммита, влияющего
на файлы, которые читает облачная Routine-сессия (`.mcp.json`,
`.claude/settings.json`), проверять `git status --branch` на `ahead N` и
пушить сразу, иначе Routine работает со старой версией репозитория.

### 2. `.mcp.json` требует прикреплённый репозиторий у Routine

Отдельно от пункта 1 — сама Routine должна иметь репозиторий в **Select
repositories** при создании. У `shopping`/`watchdog` репозиторий не выбран
(не нужен, промпт самодостаточен) — `grocery` первый агент, которому он
нужен именно из-за `.mcp.json`.

### 3. Задержка на permission prompt для project-scoped MCP-инструментов

Каждый первый вызов `mcp__vkusvill__*` в сессии сопровождается событием
`permission prompt` в логе. Это выглядит как блокировка, ожидающая ручного
подтверждения (`worker_status: requires_action` в API), но **на практике
разрешается само**, без участия человека — задержка от ~13 секунд до
нескольких минут (наблюдался случай в 2m46s на восьми параллельных
`vkusvill_product_details`). Добавление `mcp__vkusvill__*` в
`permissions.allow` в `.claude/settings.json` не дало заметного эффекта
(тест после коммита всё равно показал `permission prompt` с задержкой) —
похоже, это внутренняя проверка платформы для MCP-серверов из `.mcp.json`
(в отличие от предустановленных account-level коннекторов, чей трафик идёт
через серверы Anthropic и не имеет этой задержки), а не обычный
permission-диалог, который решает `settings.json`. Файл оставлен в
репозитории — вреда не несёт, могло помочь в части случаев.

**Практический вывод**: агент может отвечать не мгновенно, а через
1-3 минуты, особенно на сложные запросы (рецепт → детали по нескольким
ингредиентам → корзина, как в кейсе с борщом — заняло ~6 минут суммарно).
Это платформенное ограничение, не баг промпта — не пытаться «чинить»
ускорением промпта.

### 4. Rate limit самого MCP ВкусВилла

При интенсивном тестировании подряд (несколько синтетических вызовов через
API за пару минут) `vkusvill_products_search` начал возвращать
`{"code":"rate_limited", "http_status":429}`. Агент корректно обработал это
согласно промпту — после нескольких ретраев с задержкой отправил в Telegram
сообщение об ошибке вместо молчания. **Не тестировать `grocery` слишком
часто подряд** — тот же урок, что и для `shopping` (Инцидент 4 в его
дизайн-документе про захламление сессии), только здесь ограничение на
стороне стороннего MCP, а не платформы Routines.

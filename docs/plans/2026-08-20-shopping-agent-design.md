# Дизайн: агент-покупки (Ozon / Яндекс.Маркет, по ключевому слову или фото)

Дата: 2026-08-20 (спроектирован), 2026-08-21 (доведён до рабочего состояния)
Статус: **работает** — проверено вживую в группе «Lev's assistants»

## Контекст

Третий агент из системы (см. `agents-setup-brief.md`, идея №1 «Агент-покупки»).
Отличие от первых двух (`news-digest`, `watchdog`): те работают по расписанию,
этот реагирует на конкретное сообщение в Telegram — ключевое слово («купи»,
«купить», «найди», «закажи» и т.п.), в том числе с приложенным фото.

У Routines нет нативного триггера «пришло сообщение в Telegram» — нужен лёгкий
слушатель, который дёргает Routine через API-триггер, когда что-то произошло.

Ни у Ozon, ни у Яндекс.Маркета нет открытого API — используем веб-поиск внутри
Routine (тот же подход, что в `news-digest`), а не браузерную автоматизацию.

## Архитектура: два звена

**Звено 1 — слушатель (Cloudflare Worker, без ИИ).** Telegram шлёт туда каждое
входящее сообщение (webhook), включая `business_message` из личных чатов через
секретарский режим. Слушатель грубо фильтрует по корням слов и либо дёргает
Routine, либо ничего не делает — дорогой LLM-агент не должен запускаться на
каждое сообщение в группе.

**Звено 2 — Routine `Shopping` (разовый запуск с LLM).** Получает payload от
слушателя, сам решает, реальная ли это просьба найти товар, ищет на Ozon и
Яндекс.Маркете, сравнивает и отвечает в Telegram.

### Почему Cloudflare Worker, а не Google Apps Script

Первая версия слушателя была на Apps Script (`scripts/log-sheet.gs`-подобный
паттерн — уже использовался для лога и казался естественным выбором). Не
сработало: **Apps Script Web App всегда отвечает на POST 302-редиректом** на
`script.googleusercontent.com`, а **Telegram не следует за редиректами** при
доставке в вебхук — получает `302`, засчитывает как сбой доставки
(`"Wrong response from the webhook: 302 Found"` в `getWebhookInfo`) и повторяет
попытку, иногда сразу по несколько раз, иногда с большой задержкой. Это была
причина почти всех странностей на первом круге тестирования (пропавшие,
задвоенные и сильно опоздавшие сообщения). Для Sheets-лога это не проблема
(туда стучимся сами через `curl -L` и `Routine` тоже через `curl -L` — оба
следуют за редиректом), но для **прямой цели Telegram-вебхука** Apps Script
структурно не подходит. Заменили на Cloudflare Worker — отвечает обычным `200`
сразу, без этой проблемы.

## Звено 1: слушатель — `scripts/shopping-listener-worker.js`

Деплой и апдейт секретов делались напрямую через Cloudflare API (`curl`), без
похода в дашборд — см. `docs/SETUP-GUIDE.md`, раздел 6.1.

Логика `fetch(request, env, ctx)`:

1. `GET ?debug=1` — отдельный диагностический маршрут: возвращает последний
   сырой апдейт, который видел воркер (хранится в KV). Не трогает обычную
   логику, только для ручной отладки.
2. Дедупликация по `update_id` через Workers KV (namespace `UPDATE_CACHE`,
   TTL 6 часов) — Telegram может повторно доставить один и тот же апдейт,
   если посчитал предыдущую попытку неудачной; без дедупа один реальный
   апдейт превращается в несколько параллельных запусков Routine.
3. Достать сообщение: `update.message` (группа) или `update.business_message`
   (секретарский режим).
4. **Критично: игнорировать сообщения от ботов** (`message.from.is_bot`) —
   иначе собственный ответ агента («…рекомендую купить…») сам матчится на
   триггер-слово и агент зацикливается на себя (см. инцидент ниже).
5. Определить текст-кандидат: `message.text`, либо `message.caption` (подпись
   к фото), либо текст реплая на более раннее фото.
6. Проверить текст-кандидат на корни (регистронезависимо, substring):
   `куп`, `заказ`, `найд`, `buy`, `order`, `find`.
7. Если совпало — собрать `{chat_id, message_id, business_connection_id,
   text, photo_file_id}` и вызвать Routine `fire`-эндпоинт **в фоне** через
   `ctx.waitUntil(...)`, вернув Telegram `200` немедленно, не дожидаясь
   ответа от Anthropic API. Это не просто оптимизация — именно синхронное
   ожидание было второй причиной (после 302) повторных доставок от Telegram
   на старте.

Секреты — Cloudflare Workers Secrets (`ROUTINE_TRIGGER_URL`,
`ROUTINE_TRIGGER_TOKEN`), привязка KV namespace `UPDATE_CACHE` — всё
настраивается через `PUT /accounts/{id}/workers/scripts/{name}` с
multipart-телом (metadata JSON + код), не через дашборд.

## Звено 2: промпт Routine `Shopping`

Триггер Routine — **API (`fire`)**, не расписание. Формат вызова (выяснено на
практике, нигде не было задокументировано заранее):

```
POST https://api.anthropic.com/v1/claude_code/routines/<id>/fire
Authorization: Bearer <token>
anthropic-version: 2023-06-01
anthropic-beta: experimental-cc-routine-2026-04-01
Content-Type: application/json

{"text": "..."}
```

Тело принимает **только** поле `text` — оно добавляется как обычная реплика в
сессию Routine. Именованных параметров платформа не даёт, поэтому весь payload
кладётся как JSON-строка внутрь `text`, и сам промпт разбирает этот JSON:

```json
{"chat_id": ..., "message_id": ..., "business_connection_id": "" | "...", "text": "...", "photo_file_id": "" | "..."}
```

Финальный текст промпта:

```
Ты — агент-покупки. Тебя вызывают через API-триггер каждый раз, когда в
Telegram кто-то написал что-то похожее на просьбу купить/найти товар.

КРИТИЧЕСКИ ВАЖНО: у тебя НЕТ памяти о предыдущих вызовах в этой сессии.
Каждый вызов обрабатывай так, будто это единственное и первое сообщение,
которое ты видишь. Даже если в истории сессии есть более ранние сообщения
с похожим JSON — ПОЛНОСТЬЮ ИГНОРИРУЙ их, не используй их chat_id,
message_id, text или что-либо ещё оттуда. Работай ИСКЛЮЧИТЕЛЬНО с JSON из
самого последнего (самого нижнего) сообщения сессии.

Каждый вызов добавляет отдельную реплику с JSON-строкой вида:

{"chat_id": ..., "message_id": ..., "business_connection_id": "" или "...",
 "text": "...", "photo_file_id": "" или "..."}

1. Прочитай поле text целиком (не только триггер-слово) и реши: это
   реальная просьба найти/купить конкретный товар, или слово попало
   случайно (обсуждение не по теме, слишком расплывчато — например просто
   «купи» без указания что). Если не похоже на реальный запрос — сразу
   переходи к шагу 6 со status=skipped, в Telegram НИЧЕГО не пиши.

2. Если photo_file_id не пусто:
   - вызови getFile через Bot API, получи file_path
   - скачай файл по прямой ссылке
     https://api.telegram.org/file/bot${TELEGRAM_BOT_TOKEN}/{file_path}
   - посмотри на изображение, опиши товар (категория, цвет, материал,
     бренд/модель если видно, отличительные детали)
   - это описание + любой текст из поля text (бюджет, цвет, размер и
     т.п.) вместе формируют поисковый запрос

3. Через веб-поиск найди этот товар отдельно на Ozon и на Яндекс.Маркете.
   Для каждого найденного варианта постарайся получить: цену, наличие,
   срок доставки (если виден), рейтинг/количество отзывов, прямую ссылку.

4. Выбери топ-2-3 варианта, балансируя цену/рейтинг/наличие — не всегда
   самый дешёвый, если у него плохой рейтинг или нет в наличии, объясни
   почему всё равно (или почему нет) его выбрал.

5. Отправь ответ в Telegram Bot API sendMessage, ОБЯЗАТЕЛЬНО с
   reply_to_message_id=message_id, chat_id=chat_id (оба из ПОСЛЕДНЕГО
   JSON, см. выше), и business_connection_id из того же JSON, если оно не
   пусто. Формат:

   🛒 {что искали}

   1. {название} — {цена} ₽, {Ozon/Я.Маркет}, ★{рейтинг} ({N} отзывов), {наличие/срок}
      {ссылка}
      {1 фраза почему хороший вариант}

   2. ...

   💡 {краткая рекомендация: что бы взял сам агент и почему}

   Если поиск не дал внятных результатов — короткое сообщение об этом
   вместо молчания.

6. Залогируй запуск на Sheets-вебхук (как остальные агенты):

   curl -s -L -X POST "${SHEETS_LOG_URL}" \
     -d "token=${SHEETS_LOG_TOKEN}" \
     -d "agent=shopping" \
     -d "status=success|skipped|error" \
     -d "timestamp=$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

Environment variables Routine (Run now → открыть сессию → ⋮ → Edit
environment): `TELEGRAM_BOT_TOKEN`, `SHEETS_LOG_URL`, `SHEETS_LOG_TOKEN`.

Для `watchdog` изменений в его коде не требуется, но его **дизайн** обновлён —
см. `2026-08-18-watchdog-agent-design.md`: агенты по событию (без суточной
нормы, как `shopping`) теперь оцениваются отдельным правилом — вспышка
>10 запусков одного агента в пределах часа = подозрение на цикл.

## Инциденты и фиксы (хронология отладки 2026-08-20/21)

Настройка заняла на порядок больше времени, чем ожидалось — не из-за одной
ошибки, а из-за нескольких независимых проблем, маскировавших друг друга.
Ниже — все они, чтобы не наступать повторно.

### 1. Self-trigger loop (~20 срабатываний за 22 минуты)

Слушатель не проверял автора сообщения. Собственный ответ бота («…рекомендую
купить…») сам матчился на триггер-слово → бесконечный цикл. Экстренная мера —
`deleteWebhook`. Постоянный фикс: игнорировать `message.from.is_bot` в самом
начале обработки, **до** любой другой логики.

### 2. Apps Script 302 vs Telegram webhook

См. раздел «Почему Cloudflare Worker» выше — структурная несовместимость,
не баг кода. Мигрировали весь слушатель на Cloudflare Worker.

### 3. Telegram ретраит недоставленные апдейты → дубли

Пока слушатель был на Apps Script (302 = «сбой» с точки зрения Telegram), один
реальный апдейт мог доставляться по 5-6 раз подряд. Фикс: дедуп по
`update_id` через KV (сохранился и после переезда на Worker — Telegram может
ретраить и по другим причинам, например при таймауте).

### 4. Захламление сессии Routine (повторяющийся баг)

Routine API-триггер (`fire`) добавляет каждый вызов как реплику в **одну и ту
же** непрерывную сессию, а не создаёт новую сессию на каждый вызов. После
нескольких тестов подряд (личка, группа, синтетика) сессия накапливает много
сообщений, и модель периодически «откатывалась» к chat_id/тексту из более
раннего сообщения вместо самого свежего — сообщение уходило не в тот чат
(классически: написал в группу, ответ пришёл в личку). Инструкция «бери
только последнее сообщение» в промпте снижает частоту, но не убирает
полностью при большом накоплении истории.

**Рабочий фикс на сейчас**: при признаках путаницы чатов — удалить Routine и
создать заново (чистая сессия). У Routines с триггером по расписанию есть
`Archive` для сессии (⋮ в открытой сессии) — у Routines с API-триггером такого
пункта в UI замечено не было, поэтому единственный проверенный способ сброса
— пересоздание. При пересоздании: новый `fire`-URL и токен, обновить их в
Cloudflare Worker (Environment variables), Environment variables самой
Routine выставить заново.

**Практический вывод**: не тестировать одну и ту же Routine избыточно много
раз подряд (личка вперемешку с группой, синтетика вперемешку с реальными
сообщениями) — это и есть то, что забивает сессию. Для реальной эксплуатации
это менее критично (частота использования ниже, чем во время интенсивной
отладки), но стоит иметь в виду как известное ограничение платформы.

### 5. Telegram Group Privacy + Inline Mode блокировали группу целиком

Самый долгий баг. Симптом: в личке всё работало стабильно, в группе — тишина,
причём апдейт не доходил даже до `getUpdates` (не проблема вебхука/кода,
Telegram сам не ставил апдейт в очередь). Причины наложились две:

- **Group Privacy** был включён на боте изначально; выключение в настройках
  бота **не применяется к уже открытым чатам** — нужно удалить бота из группы
  и добавить заново, чтобы новая настройка подхватилась именно для этого
  чата. Проверено эмпирически: даже в **новой, только что созданной** группе
  один только тумблер иногда не помогал, пока не выключили и второе:
- **Inline Mode** был включён. Если сообщение начинается с `@ИмяБота`,
  Telegram-клиент перехватывает его на уровне поля ввода как inline-запрос —
  сообщение вообще не отправляется в чат как обычное. Не связано напрямую с
  Group Privacy, но давало похожий симптом (тишина) в сценариях, где
  по привычке хотелось «позвать» бота через `@`.

**Фикс**: в настройках бота — Group Privacy выключен, Inline Mode выключен.
После любого изменения этих настроек — **обязательно** удалить бота из
группы (в т.ч. «Lev's assistants») и добавить заново, иначе старое состояние
держится в уже открытом чате.

### 6. Sheets-логирование иногда «Page Not Found» изнутри Routine

Разово Routine сообщила, что `SHEETS_LOG_URL` вернул `Google Drive Page Not
Found` вместо ответа Apps Script — при том что тот же URL, вызванный вручную
(`curl -L`), отвечал нормально (302 → валидный редирект). Похоже на разовую
неполадку (возможно, квота Apps Script после интенсивного тестирования), не
воспроизвелась стабильно — не чинили специально, если повторится системно,
разбираться отдельно.

## Порядок настройки (актуальный, см. также `docs/SETUP-GUIDE.md` раздел 6)

1. В настройках бота (BotFather / нативный Bot Settings UI): Group Privacy —
   выключить, Inline Mode — выключить, Secretary Mode — оставить включённым
2. Создать Cloudflare Worker из `scripts/shopping-listener-worker.js`,
   привязать KV namespace, задать секреты (`ROUTINE_TRIGGER_URL`,
   `ROUTINE_TRIGGER_TOKEN`) — можно полностью через Cloudflare API (`curl`),
   без дашборда
3. Создать Routine `Shopping` с промптом выше, триггер — API; Run now → Edit
   environment → добавить `TELEGRAM_BOT_TOKEN`, `SHEETS_LOG_URL`,
   `SHEETS_LOG_TOKEN`
4. Зарегистрировать Worker как Telegram-вебхук (`setWebhook`, `allowed_updates`
   включая `business_message`)
5. Удалить бота из рабочей группы и добавить заново (чтобы настройки privacy/
   inline точно подхватились для этого чата)
6. Прогнать вручную: текстовый запрос в группе, фото с подписью «купи»,
   нерелевантное сообщение с «купить» (должно тихо промолчать со
   status=skipped)
7. Если появляется путаница с чатами (ответ не туда) — пересоздать Routine
   (см. инцидент №4)
